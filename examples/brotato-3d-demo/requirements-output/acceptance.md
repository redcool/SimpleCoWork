```markdown
# acceptance.md

## 1. 目标
将“做一个3D的土豆兄弟”这一想法转化为可评审、可执行的技术与艺术规格说明，作为向开发（3D美术/程序）与关卡策划交接的需求基线。

## 2. 事实（Facts）
- 源参考：《土豆兄弟》（Brotato）是一款 2D 俯视角、回合制波次生存射击 + Roguelite 肉鸽成长向游戏。
- 输入需求文本：“做一个3d的土豆兄弟”。
- 输入中未提供任何技术选型、美术资产、关卡结构、数值表或交互清单。
- 输入中未提供任何代码、工程文件、Git 仓库或版本管理信息。

## 3. 假设（Assumptions）
以下均为假设，需后续由设计、程序与美术逐项确认，确认前不作为“事实”对待：
- A1：将“3D”理解为渲染视角为 3D（俯视/斜视角），而非完全自由 3D 漫游（FPS/TPS 自由视角）。  
- A2：保留 Brotato 核心循环：固定角色、回合（Round）制、波次生存、商店局内购买、局外成长（升级角色/特性）。  
- A3：采用 Unity 或 Unreal 作为引擎候选（待程序确认）。  
- A4：3D 化后，俯视角摄像机与 2D 碰撞检测/寻路逻辑需重新实现（Bolt、Bread 等敌人 AI 需要 3D 化）。  
- A5：角色与敌人均为低多边形/风格化卡通 3D 模型，贴图风格需与 2D 原版的可爱/简约风格保持视觉统一。  
- A6：局内商店、装备槽位、数值成长体系与 2D 原版逻辑保持一致，仅将表现层替换为 3D。  
- A7：不引入网络多人功能（单机本地）。  
- A8：平台优先级：PC 首发；移动端延后（视 3D 化性能评估结果）。  
- A9：帧率目标：60 FPS（1080p）在中端独显 PC 上达到。

## 4. 可验收标准（Acceptance Criteria）
每条标准包含：可验证内容 + 证据方式。所有标准必须通过后才可进入“可开发”状态。

### AC1：3D 俯视角场景与摄像机
- 验收点：
  - 角色位于一个 3D 俯视角场景中，摄像机跟随角色，视角固定为斜 45° 或可调 30°–60°。
  - 场景中地面有网格或边界墙，可清晰看到“房间”轮廓。
- 证据：
  - 构建一个最小场景（角色 + 地面 + 摄像机），录制 10 秒视频展示跟随效果与视角。
  - 提供截图标注摄像机参数（距离、角度、FOV）。

### AC2：角色 3D 模型与基础动画
- 验收点：
  - 主角“土豆兄弟”的 3D 模型完成（低多边形，面数 ≤ 2000 tris）。
  - 包含 4 个基础动画：待机、跑动、攻击（开火）、受击。
  - 动画在 3D 场景中正常播放，无穿模或抖动。
- 证据：
  - 提供 FBX/glTF 资产文件及动画时间轴截图。
  - 在编辑器中播放动画，录制 8 秒视频。

### AC3：武器与攻击表现
- 验收点：
  - 至少实现 2 种武器（如：手枪、霰弹枪）的 3D 模型与开火动画。
  - 子弹为 3D 胶囊体或球形，按射线/物理方式飞出，命中敌人有基础特效（粒子或缩放反馈）。
  - 攻击命中时敌人受击动画播放，生命值减少。
- 证据：
  - 在最小场景中放置 1 个敌人，录制 15 秒视频展示两种武器的开火与命中效果。
  - 提供命中逻辑伪代码或函数说明（不要求最终代码，但需有可运行演示）。

### AC4：敌人 AI 与 3D 化
- 验收点：
  - 实现至少 1 种敌人（如“面包”），包含 3D 模型与基础移动/攻击动画。
  - 敌人按回合波次生成，向主角移动（3D 寻路或直线追踪），攻击范围与 2D 原版保持一致。
  - 敌人生成与销毁逻辑与回合系统联动。
- 证据：
  - 录制 30 秒视频：展示 2 个回合，敌人从波次生成、移动、攻击、被击杀的完整循环。
  - 提供敌人生成/销毁的状态机图或逻辑说明文档。

### AC5：回合（Round）系统与 UI
- 验收点：
  - 回合计数 UI 在 3D 场景中可见（屏幕空间 UI）。
  - 回合间展示商店界面（可为 2D UI 覆盖 3D 场景，不要求商店本身 3D 化）。
  - 回合结束后自动进入商店，购买后自动进入下一回合。
- 证据：
  - 录制 20 秒视频展示：回合结束 → 商店弹出 → 购买 → 下一回合开始的完整流程。
  - 提供 UI 布局截图与交互说明。

### AC6：性能基线
- 验收点：
  - 在 1080p、中高画质设置下，场景中同时存在 ≤ 20 个敌人、主角 + 2 武器、基础粒子效果时，帧率 ≥ 60 FPS。
  - 绘制调用（Draw Calls）≤ 50。
- 证据：
  - 提供 Profiler 截图（CPU/GPU/Draw Calls）与帧率曲线图。
  - 测试平台与显卡型号需明确标注。

### AC7：局内数值与成长（逻辑层）
- 验收点：
  - 主角有 3 个可升级属性（如攻击力、生命值、移动速度），升级逻辑与 2D 原版一致。
  - 局外成长系统至少保留 1 条路线（如：击杀累计解锁新角色或新特性）。
- 证据：
  - 提供数值表（CSV/JSON）与升级逻辑说明。
  - 在编辑器中模拟 1 局游戏，验证属性随升级正确变化。

### AC8：技术资产交接包
- 验收点：
  - 提供最小可运行构建（PC .exe 或 .zip），包含上述 AC1–AC7 全部功能。
  - 附带 README.md，说明：引擎版本、运行方式、已知限制、下一步待办。
  - 资产文件（模型、动画、粒子、UI 素材）按目录规范存放并附说明。
- 证据：
  - 上传可运行构建到项目文件管理（如 Git LFS、内部网盘），并提供访问链接。
  - 资产目录树截图。

## 5. 不做的事（Out of Scope）
以下项目不在本轮交接范围内，后续迭代另立需求：
- 完整关卡/地图设计（当前仅基础房间）。
- 网络多人 / 在线排位。
- 移动端适配与触屏操作。
- 音频 / 音效 / 背景音乐。
- 完整数值平衡与 50 回合全流程调优（当前仅验证逻辑可行性）。
- 角色皮肤 / 新角色解锁 UI。
- 成就系统 / 局外 meta 完整流程（仅保留 1 条解锁路线验证）。

## 6. 关键风险
| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 3D 俯视角寻路与 2D 原版差异导致手感偏移 | 中 | 先实现直线追踪 + 简单碰撞，后续迭代加入 A* 或 Flow Field |
| 低多边形模型在移动端性能不足 | 中 | 性能基线在 PC 上先验证，移动端为后续阶段 |
| 商店 UI 与 3D 场景的层级/遮挡冲突 | 低 | 商店使用 Screen Space Canvas，不与 3D 场景深度混合 |
| 敌人生成性能（大量对象） | 中 | 使用对象池（Object Pooling）管理敌人实例 |

## 7. 下一步行动
1. 程序：基于 AC1–AC8 搭建最小可运行场景（1 周）。
2. 3D 美术：产出主角 + 2 武器 + 1 敌人模型与动画（与程序并行，1.5 周）。
3. 策划：确认假设 A1–A9 全部条目，输出确认版假设清单。
4. 评审：按 AC 逐条验收，输出验收报告，标记通过 / 不通过 / 部分通过。
5. 进入迭代 2：扩展敌人种类、完整商店、局外 meta。
```
