# Studio CoWork 技术选型与架构讨论记录

> 归属：Studio CoWork v2 探讨资料
> 当前基线：Studio CoWork 0.1.0.0
> 更新时间：2026-09-13

## 1. 总体技术架构

Studio CoWork 面向本地工程，以大量 LLM Agent 模拟专业工作室。推荐分层：

~~~text
LLM Agent：需求理解、策划、设计、编码、资源生产、审查和决策建议
框架：版本、阶段、依赖、审批、权限、安全、调度和审计
SQLite：当前工程元数据、关系和可查询索引
本地文件：文档、代码、图片、模型、动画、音频、测试报告和构建包
JSONL：不可变事件流、回放、审计和 SQLite 重建
~~~

核心原则是：LLM 决定做什么和为什么做；框架决定能否执行、写入哪里、是否批准和如何记录。

## 2. JavaScript 与 TypeScript

### 当前决策：继续 JavaScript

Studio CoWork 0.1.0.0 使用 Node.js ESM JavaScript。优势：

- 与 CoWork v1 兼容，迁移成本最低；
- Node.js 可直接运行，保持零构建和低依赖；
- node:test 可以直接验证；
- Agent 修改和生成 JavaScript 更直接；
- 领域模型仍在探索，接口调整速度快；
- CLI、SQLite、文件系统和 Provider 适配快速。

### TypeScript 的长期优势

- Version、Stage、Artifact、Approval、Bug 获得静态约束；
- 跨模块 API 和状态枚举更安全；
- 多人维护和大型重构更可靠；
- 适合未来拆分 cowork-core/cowork-studio。

### 迁移策略

暂不迁移，避免同时进行领域重构和编译链重构。等 Studio API 稳定、核心模块明显增多、多人长期维护或准备独立发布时再迁移。过渡期使用 JSDoc、集中状态迁移、边界校验和 node:test。

## 3. SQLite 与 PostgreSQL

### 当前决策：SQLite

Studio CoWork 目前是本地工程、单机调度、单项目或少量项目、无异地多机共享。SQLite 的单文件特性是优势：

- 工程可携带、可复制、可归档；
- 数据库和文档/代码/资源位于同一工程上下文；
- 无服务启动、端口、账号和网络依赖；
- 备份和恢复简单；
- 每个工程可以数据隔离；
- ACID、外键、唯一约束和事务适合阶段门、审批和封版。

SQLite 的边界：不适合多机同时写、远程多用户、高并发队列和集中式多租户服务。

### PostgreSQL 何时使用

当需求变为多计算机异地工程、远程协作、多用户在线审批、高并发 Agent 写入或高可用服务时，再迁移 PostgreSQL。当前不迁移，因为服务化运维复杂度不能换来本地模式的实际收益。

### 设计要求

业务代码不得散落 SQLite 特有 SQL。通过 Repository/Store 边界封装数据库，显式 UUID 作为业务 ID，不依赖 rowid；时间使用 ISO 8601；Schema 有迁移版本。未来可实现 PostgresRepository 替换 SQLiteRepository。

## 4. SQLite 与 NoSQL

### 当前决策：不使用 NoSQL 作为事实库

Studio 数据是强关系数据：

~~~text
Project → Version → Stage → Task → Artifact → Dependency
                         ↓
                  Review / Approval / Release
Bug → Impact → Artifact → Stage → Regression Test
~~~

典型查询需要外键、事务、索引和 JOIN。NoSQL 会把依赖、继承、影响分析和阶段门一致性转移到应用层，增加重复数据和一致性风险。

NoSQL 适合 Schema 高度变化、海量事件、水平扩展和整条文档读取。未来可作为 Agent 会话、缓存或非结构化知识的补充，但不应替代版本、审批、Artifact 依赖和发布状态的关系事实库。

远程版可采用：PostgreSQL 做关系主库；Redis 做队列、锁和缓存；对象存储做大型资源；搜索/向量数据库做检索。

## 5. 文件系统与数据库的边界

本地文件保存内容：

- Markdown、JSON、CSV；
- 源代码和补丁；
- 图片、模型、动画、音频；
- 测试报告和构建包；
- release manifest。

SQLite 保存元数据和关系：

- 路径、类型、大小、checksum；
- Artifact、版本、生产者、来源；
- 依赖、审批、阶段、Bug、Release；
- 文件与 Artifact 的映射。

不把大型二进制主体塞进 SQLite。数据库损坏时，由 JSONL、manifest 和文件 checksum 重建索引。

## 6. JSONL 事件日志

JSONL 是不可变事件流，记录 project.created、version.created、stage.started、artifact.submitted、approval.granted、artifact.stale、bug.created、release.sealed 等事件。

SQLite 表示当前索引，JSONL 表示发生过什么。关键数据库写入与事件记录应具有明确顺序；长期可升级为事件先写、索引后更新，并提供重建命令。

## 7. 版本与目录

~~~text
project/
├── .cowork/project.db
├── .cowork/events.jsonl
├── releases/YYYY-MM-DD-vX.Y.Z.W/  # 只读封版
├── workspaces/YYYY-MM-DD-vX.Y.Z.W/ # Agent 工作区
└── shared/                         # 可选共享资源
~~~

每个工程默认一个 project.db。若需要跨工程查询，可增加可选 catalog.db，但工程 project.db 仍是事实源。

## 8. Agent 与权限

Agent 通过批准 Artifact 交接，不共享未追踪临时状态。每个 Agent 使用隔离 workspace，框架限制读写范围、命令白名单、文件大小、动作数量、Token 预算和超时。

框架不硬编码具体玩法、艺术和代码实现；它只提供任务、依赖、提交、审核、审批、影响分析、过期、封版和恢复原语。

## 9. 技术决策摘要

| 决策 | 当前选择 | 未来升级 |
|---|---|---|
| 运行时 | Node.js ESM JS | 稳定后迁移 TS |
| 主数据 | SQLite | 多机时 PostgreSQL |
| 内容 | 本地文件 | 对象存储（远程） |
| 事件 | JSONL | 集中事件流（远程） |
| 检索 | SQLite 索引 | 搜索/向量数据库补充 |
| 调度 | 单机 Scheduler | Redis/服务化队列 |

## 10. 最终结论

Studio CoWork 当前应坚持：

~~~text
每个本地工程一个 SQLite project.db
文件系统保存实际内容
JSONL 保存不可变事件
Repository 隔离数据库实现
未来按规模从 SQLite 升级 PostgreSQL，而不是现在提前服务化
~~~

这是与当前产品边界最匹配的方案。
