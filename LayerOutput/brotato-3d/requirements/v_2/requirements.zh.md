# 需求文档：3D 版《土豆兄弟》 (Brotato Clone)

**文档版本**: 1.0
**状态**: 初始草案 (Draft)
**输入来源**: 用户一句话需求 “做一个3d的土豆兄弟”
**作者**: 策划组组长

## 1. 概述与目标

### 1.1 核心愿景
将经典 2D 俯视角 Roguelite 生存游戏《Brotato》(土豆兄弟) 的核心玩法移植至 3D 引擎，保留其“短局时制、武器堆叠、角色选择、卡牌/配件成长”的核心循环，但利用 3D 空间增加战术深度（如 Z 轴站位、掩体利用）。

### 1.2 目标平台
*   **事实**: 输入仅提及“3D”，未指定引擎或平台。
*   **假设**: 为最大化开发效率与美术表现力，目标引擎暂定为 **Unity 3D** (LTS 版本) 或 **Unreal Engine 5**。
*   **建议**: 鉴于《土豆兄弟》是轻量级独立游戏，Unity 在团队小型化和迭代速度上更具优势，本文档后续验收标准基于 Unity C# 架构假设。
*   **目标平台**: PC (Steam), Mobile (iOS/Android, 适配触屏)。

### 1.3 非目标 (Out of Scope)
*   不追求 AAA 级画质。
*   不包含多人在线合作/对战（首版仅为单机单人）。
*   不重建《土豆兄弟》的所有 30+ 个角色，首版仅实现 5-10 个代表性角色用于验证核心循环。

## 2. 核心玩法定义 (Key Gameplay Loop)

### 2.1 游戏流程 (Fact-based on Brotato Mechanics)
1.  **角色选择 (Character Select)**: 玩家从列表中选择一个拥有特定属性加成的角色。
2.  **初始装备**: 随机获得 3-5 件初始武器/配件。
3.  **房间战斗 (Arena Combat)**:
    *   每轮 (Round) 持续 60-90 秒。
    *   敌人从地图边缘生成，向中心/玩家位置进攻。
    *   玩家控制角色在有限空间内移动、射击、闪避。
    *   目标：存活并尽可能清除敌人。
4.  **奖励阶段 (Reward Phase)**:
    *   战斗结束后，玩家获得金币。
    *   玩家进入商店，可购买新武器、升级现有武器、购买配件或药水。
    *   玩家可选择升级角色技能（若有）或重新滚刷新装备池。
5.  **循环**: 重复步骤 3-4，直到角色死亡或达到游戏设定的最大轮数（如第 10 轮或最终 Boss 轮）。

### 2.2 3D 差异化设计 (Assumptions & Design Decisions)
*   **事实**: 2D Brotato 中，玩家和敌人均在同一平面，无 Z 轴概念。
*   **设计决策**:
    1.  **视角**: 采用 **斜 45 度俯视 (Top-Down / Third-Person)**，而非第一人称，以保持信息密度和快速反应节奏。
    2.  **空间限制**: 战斗地图为封闭的 3D 房间，四周有墙体或围栏。地图中心可能有高台、箱子等障碍物。
    3.  **Z 轴交互**: 敌人主要在地面活动，但部分特殊敌人（如飞行物、跳跃物）利用 Z 轴突袭。玩家可通过跳跃（若赋予角色跳跃能力）躲避地面攻击，但跳跃增加被集火风险。
    4.  **碰撞检测**: 3D 碰撞箱需比 2D 更精细，防止穿模。

## 3. 详细功能需求

### 3.1 角色系统 (Character System)

| ID | 功能描述 | 优先级 | 验收标准 (Acceptance Criteria) | 事实/假设 |
|:---|:---|:---:|:---|:---|
| C-01 | 角色属性定义 | P0 | 每个角色拥有 5 维基础属性：攻击力、生命值、移速、暴击率、幸运值。属性在 UI 面板实时显示。 | 事实 (源自 Brotato) |
| C-02 | 角色列表 | P0 | 首版提供至少 5 个角色。每个角色有唯一 ID、名称、图标、基础属性倍率。 | 假设 (原游戏有30+，此处缩减) |
| C-03 | 角色被动技能 | P1 | 每个角色拥有一个可激活或自动触发的被动技能。例如：“攻击速度+20%” 或 “击杀后回血 5%”。 | 事实 |
| C-04 | 角色模型加载 | P0 | 选择角色后，3D 场景中的玩家模型需替换为对应角色的 3D 模型（低多边形风格）。 | 假设 (3D 特有) |

### 3.2 战斗系统 (Combat System)

| ID | 功能描述 | 优先级 | 验收标准 (Acceptance Criteria) | 事实/假设 |
|:---|:---|:---|:---|:---|
| G-01 | 玩家移动 | P0 | 玩家通过 WASD/手柄右摇杆/屏幕虚拟摇杆移动。移动受地形碰撞体限制，不可穿过墙壁。帧率稳定在 60FPS 下，移动响应延迟 < 50ms。 | 假设 (3D 输入) |
| G-02 | 自动瞄准 | P0 | 玩家无需手动瞄准。武器根据“最近敌人”或“玩家面对方向”自动射击。若玩家面对无敌人，则停止射击（不盲射）。 | 事实 (Brotato 核心) |
| G-03 | 武器射速 | P0 | 射速 (Rate of Fire) 影响每秒射击次数。不同武器有不同射速、射程、伤害。数值需在配置表中可调整。 | 事实 |
| G-04 | 敌人 AI | P0 | 敌人行为模式：\n1. **普通**: 直线走向玩家。\n2. **远程**: 保持距离，间隔射击。\n3. **精英**: 高血量，高伤害，特定攻击模式。\n敌人生成逻辑：每轮开始前生成波次，随轮数增加，数量和强度提升。 | 事实 |
| G-05 | 伤害判定 | P0 | 子弹/投射物与敌人碰撞箱相交时扣除血量。敌人血量归零时播放死亡特效并掉落金币。 | 事实 |
| G-06 | 3D 投射物 | P1 | 子弹在 3D 空间中飞行，具有重力（可选）或直线弹道。需处理 Z 轴遮挡（如子弹飞越障碍物）。 | 假设 (3D 特有) |

### 3.3 经济与成长系统 (Economy & Progression)

| ID | 功能描述 | 优先级 | 验收标准 (Acceptance Criteria) | 事实/假设 |
|:---|:---|:---|:---|:---|
| E-01 | 金币获取 | P0 | 击杀敌人掉落金币。金币吸附至玩家身边（磁吸范围 2m）。每轮结算剩余金币。 | 事实 |
| E-02 | 商店系统 | P0 | 轮次结束后，随机生成 3-5 个商品。商品类型：武器、配件、药水、重开 (Reroll)。价格基于商品稀有度和当前轮数。 | 事实 |
| E-03 | 武器升级 | P0 | 已有武器可花费金币升级（Lv1->Lv5）。升级后增加伤害、射速或改变弹道。 | 事实 |
| E-04 | 配件槽位 | P0 | 角色拥有固定数量的配件槽（如 3 个）。配件提供全局属性加成（如 +10% 移速）。 | 事实 |
| E-05 | 稀有度系统 | P1 | 商品分为：普通、罕见、史诗、传说。不同稀有度有不同颜色标识和更高基础数值。 | 事实 |

### 3.4 UI/UX 设计

| ID | 功能描述 | 优先级 | 验收标准 (Acceptance Criteria) | 事实/假设 |
|:---|:---|:---|:---|:---|
| UI-01 | 战斗 HUD | P0 | 屏幕底部显示当前装备栏（图标+等级+状态）。屏幕顶部显示：当前轮数、倒计时、角色头像、血量条。 | 事实 |
| UI-02 | 伤害数字 | P0 | 命中时显示浮动伤害数字。暴击伤害需有不同颜色/大小。数字需跟随 3D 位置并在屏幕上投射，确保不被模型完全遮挡。 | 假设 (3D UI 技术点) |
| UI-03 | 地图指示器 | P1 | 屏幕边缘小地图或箭头指示，显示下一波敌人主要进攻方向（可选功能，降低压迫感）。 | 假设 |

## 4. 技术架构与数据需求

### 4.1 数据配置 (Fact/Assumption Mixed)
*   **假设**: 使用 JSON 或 ScriptableObjects (Unity) 管理所有数值平衡。
*   **需求**:
    *   `CharacterConfig`: 定义角色 ID、名称、基础属性、被动技能 ID。
    *   `WeaponConfig`: 定义武器 ID、名称、基础伤害、射速、射程、弹道类型、预制体路径。
    *   `EnemyConfig`: 定义敌人 ID、血量、速度、攻击方式、出生权重。
    *   `ItemConfig`: 定义商店商品价格曲线、稀有度概率表。

### 4.2 3D 场景与性能 (Assumption)
*   **美术风格**: 低多边形 (Low Poly) 风格，色彩鲜艳，符合《土豆兄弟》可爱、休闲的调性。
*   **性能指标**:
    *   目标帧率: 60 FPS (PC), 30 FPS (Mobile Low-End)。
    *   Draw Call: 战斗中同屏敌人数量 ≤ 50 时，Draw Call 应优化至 < 100 (通过合批或 GPU Instancing)。
    *   内存占用: 移动端包体大小目标 < 50MB (不含资产缓存)。

### 4.3 核心代码模块 (High-Level)
*   `PlayerController`: 处理输入、移动、动画状态机。
*   `WeaponManager`: 管理装备栏、冷却计时器、投射物生成。
*   `EnemySpawner`: 控制波次生成、路径查找（使用 Unity NavMesh 或自定义 2.5D Grid 以避免复杂 3D 寻路开销）。
*   `GameLoop`: 状态机管理 (SelectChar -> Combat -> Shop -> NextRound -> GameOver)。

## 5. 风险与依赖

| 风险项 | 影响 | 缓解措施 | 状态 |
|:---|:---|:---|:---|
| **3D 性能瓶颈** | 移动端上同屏大量敌人+特效导致掉帧。 | 使用对象池 (Object Pooling)；限制同屏敌人数上限；LOD 技术简化远处模型。 | 高风险 |
| **数值平衡难度** | 3D 空间增加了走位灵活性，可能导致原有 2D 数值体系失效（太容易或太难）。 | 早期进行 Playtest，建立“轮数-平均 DPS”监控仪表盘，快速迭代数值表。 | 中风险 |
| **投射物遮挡** | 3D 中模型可能遮挡子弹，玩家不知道敌人被击中。 | 子弹碰撞检测独立于渲染；添加“穿透”材质效果或短暂高亮受击模型。 | 低风险 |
| **引擎选择未定** | 若最终选 UE5，C# 方案需重写为 C++/Blueprints。 | 本策划文档聚焦逻辑与数值，引擎无关。技术组需在 1 周内锁定引擎。 | 阻塞项 |

## 6. 里程碑计划 (MVP)

1.  **Week 1-2: 原型 (Vertical Slice)**
    *   完成玩家 3D 移动、一个角色的自动射击、一种普通敌人的生成与攻击。
    *   验证 3D 视角下的手感与性能。
2.  **Week 3-4: 核心循环**
    *   实现完整的“战斗-商店-下一轮”循环。
    *   实现 3 种武器、3 个角色、3 种敌人。
    *   UI 基础搭建。
3.  **Week 5: 内容填充**
    *   扩充至 5 角色、10 武器、5 敌人、配件系统。
    *   数值平衡初步调整。
4.  **Week 6: 优化与测试**
    *   性能优化、内存泄漏修复。
    *   邀请内部 5-10 人进行 Beta 测试，收集反馈。

## 7. 验收证据 (Evidence of Completion)

1.  **可玩性测试**: 提供一个 Build，玩家能从头开始，通过商店购买武器，存活过第 5 轮，并体验角色死亡/通关流程。
2.  **性能报告**: 提供 Unity Profiler / Unreal Insights 截图，证明在目标硬件上满足帧率指标。
3.  **配置表验证**: 修改 `WeaponConfig` 中的伤害值，重启游戏后，实际伤害变化符合配置，无需改代码。
4.  **UI 完整性**: 所有关键状态（血量、金币、轮数、倒计时）在战斗中实时准确更新，无不同步现象。
