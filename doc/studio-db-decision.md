# Studio CoWork 数据库选型决策

## 结论

Studio CoWork v0.1.0.0 采用 **SQLite 关系型数据库 + 本地文件系统 + JSONL 事件日志**，暂不引入 NoSQL 数据库。

## 为什么更适合 SQLite

Studio CoWork 的核心数据具有强关系和强一致性：项目包含多个版本；版本包含阶段、任务和 Artifact；Artifact 具有依赖、继承和影响关系；Artifact 需要专业审核、经理审核和用户确认；Bug 关联版本、阶段、产物和测试；Release 需要完整 manifest；阶段门要求事务性状态迁移。

典型查询包括：哪些 Artifact 基于某个策划文档；哪些产物因变更变成 stale；用户批准了哪些版本；某个 Bug 影响哪些任务和测试；哪些阶段阻塞发布；某个 release 使用了哪些文件和 checksum。SQLite 的外键、唯一约束、事务、索引和 JOIN 适合这些需求。

## SQLite 优势

- 关系、依赖和审批模型自然。
- ACID 事务适合阶段门和封版。
- 外键和唯一约束防止孤儿关系与重复版本。
- 单文件部署，适合单项目和单机 Agent 编排。
- 查询、备份、迁移和恢复成本低。
- 与文件系统、Git、JSONL 易于组合。
- Node.js 24 提供 `node:sqlite`，当前无需额外驱动。

## SQLite 劣势

- 高并发写入能力有限。
- 不适合作为跨机器共享数据库。
- 不适合直接保存大量图片、模型、音频和构建包。
- Schema 变更需要迁移。
- 多用户远程工作室规模扩大后需要服务化数据库。

## NoSQL 优势

NoSQL 适合 Schema 高度变化、海量事件、水平扩展、跨地域写入和以单条文档读取为主的系统。它也适合作为 Agent 会话、缓存或非结构化知识的补充存储。

## NoSQL 劣势

对 Studio CoWork 当前核心流程，NoSQL 需要在应用层维护 Artifact 依赖、版本继承、Bug 影响关系和阶段门一致性；JOIN 查询变成多次查询或预聚合；重复数据容易产生版本不一致；本地单机还需要额外服务和运维。

## 何时考虑 NoSQL

当多机 Agent 并发写入、多用户远程协作、事件量超过单机能力、需要跨地域高可用，或 Agent 会话/向量检索成为主要负载时再评估。届时建议优先迁移到 PostgreSQL 作为关系主库，而不是直接把核心关系模型改成 NoSQL。

可组合的未来架构：PostgreSQL 管关系主库；Redis 管队列、锁和缓存；对象存储管大文件；搜索引擎管全文；向量数据库管语义检索。审批事实仍以关系主库为准。

## 推荐分层

~~~text
SQLite：项目/版本/阶段/任务/Artifact/依赖/审批/Bug/Release 元数据
文件系统：Markdown/JSON/CSV/代码/图片/模型/动画/音频/构建包
JSONL：不可变事件流、调试、审计和数据库重建
~~~

## 最终决策

Studio CoWork 当前是本地、单项目、强关系、重审计的工作流系统，SQLite 比 NoSQL 更合适。数据库只保存索引和关系，不取代内容文件；JSONL 负责事件事实，SQLite 负责当前可查询索引。
