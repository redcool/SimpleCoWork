## 2. 总体评价

项目最有价值的方向，是以版本化 Artifact、依赖、审批和阶段门组织 Agent 协作，而不是依靠聊天记录协调生产。生产与审核分离、批准输入、变更影响分析、封版只读等原则符合真实生产需求。SQLite 保存关系、文件系统保存内容、JSONL 留存审计记录，也适合当前本地工作室定位。

当前重点应从增加角色和功能转向验证核心不变量：产物内容不可被悄悄覆盖，批准必须对应明确版本和内容，下游使用的基线可追溯，失败后可以恢复。保留 JavaScript 与零运行时依赖是可接受的选择，不必为了形式立即迁移 TypeScript。

## 3. 已确认的问题与建议

### R01【P0】同名文档提交会覆盖旧 Artifact 对应文件

**依据：** `src/studio/documents.js` 的 `submit()` 每次生成新 UUID，但始终写入 `documents/<name>.<format>`，使用 `writeFileSync` 覆盖内容。该模块内未见针对已有名称的拒绝或版本化存储。

**风险：** 同名重试、返工或直接调用 Store 时，新旧 Artifact 可能对应同一个可变文件；数据库中的旧 checksum 不再代表磁盘实际内容。上层即使限制了任务名称唯一，也不等于产物内容不可变。

**建议：** 按 Artifact ID、修订号或内容哈希保存不可变文件；逻辑名称单独映射到当前版本。审批和 manifest 必须绑定具体 Artifact 与 checksum。

**验收：** 连续提交两次同名不同内容文档，旧产物仍可读取原内容且 checksum 匹配；新产物获得独立路径与身份。

### R02【P0】文件、数据库及事件提交缺少完整失败一致性

**依据：** `src/studio/documents.js` 依次执行写文件、插入 Artifact、逐条插入依赖、追加事件，没有包裹这些数据库写入的事务；`src/studio/events.js` 独立追加 JSONL。

**风险：** 外键失败、磁盘写入失败或进程崩溃，可能留下孤立文件、部分依赖或缺失事件。单纯给 SQLite 加事务，也不能自动覆盖文件系统和 JSONL。

**建议：** 数据库内提交使用事务；文件采用临时文件和明确的提交/恢复协议；审计事件可采用事务性 outbox，再幂等导出 JSONL。明确每类事实的权威来源及启动时对账策略。

**验收：** 在写文件、插入元数据、插入依赖、写事件等边界注入失败，恢复后不出现半提交产物或遗漏审批事实。

### R03【P1】数据库版本号不等于迁移机制

**依据：** `src/studio/db.js` 设置 `SCHEMA_VERSION = 2`，执行 `CREATE TABLE IF NOT EXISTS` 后直接写入当前版本号，没有先读取旧版本并按版本执行迁移。

**风险：** 已有表缺列或约束变化时，建表语句不会升级旧结构，但 schema 版本号可能已经被标记为最新。

**建议：** 增加逐版本迁移、事务、失败回滚及未知高版本拒绝策略。

**验收：** 使用真实旧版数据库夹具升级；确认数据保留、表结构正确、迁移可重复执行，失败时不会推进版本号。

### R04【P1】输入审批策略与权威状态核验需要收紧

**依据：** `src/studio/runner.js` 允许 `approved`、`user-approved` 和 `internal-approved`，仅检查调用者传入的 `a.state`；构造函数接收的 Artifact Store 未被用于读取权威状态。需求基线第 2 节强调 approved 或 user-approved 输入，阶段门另有用户确认要求。

**风险：** 旧对象可能仍显示已批准，而数据库中的产物已 stale；哪些场景允许 internal-approved 也缺少此入口处的显式策略。是否存在上层统一拦截，需继续沿调用链验证，不能据此断言全部流程均可绕过。

**建议：** 执行前按 ID 重新读取权威 Artifact，结合阶段、版本、审批策略和 checksum 检查正式输入；明确内部批准与用户批准的适用范围。

**验收：** 传入过期状态对象、跨版本非法输入、待用户确认输入时，正式任务被拒绝；合法内部生产场景仍可运行。

### R05【P1】结构化协议与审批记录约束仍较弱

**依据：** Runner 对输出主要检查 JSON 可解析、`done === true` 和 content 类型；Document Store 检查非空、格式白名单及 JSON 语法，但未验证具体文档业务 Schema。`ApprovalStore.decide()` 验证 decision 枚举，却未在该方法内验证 approverType、Artifact 与版本归属；approvals 表的 artifact_id 也没有外键。

**风险：** 形式合法不代表产物完整；底层 API 可能接受错误归属的审批。身份认证和生产者自审限制是否在上层落实，尚需单独核对。

**建议：** 为正式产物定义类型化契约和最小验收标准；在业务边界及数据库关系层共同校验审批归属、审批者身份和权限；审批应可追踪到具体内容版本。

**验收：** 缺字段文档、错误版本审批、不存在 Artifact、非法审批角色及不允许的自审路径均有拒绝测试。

### R06【P1】Node 运行时要求与 SQLite 实现不一致

**依据：** `package.json` 与需求基线仍写 Node.js >=20，而 `src/studio/db.js` 顶层直接导入 `node:sqlite`；数据库决策文档采用 Node.js 24 的内置 SQLite。Node.js 20 不提供该内置模块。

**建议：** 为 v2 统一声明并验证实际支持的 Node 版本（例如选择 Node.js 24 LTS），或者实现与声明匹配的受控 SQLite 适配层；不要同时保留不成立的兼容承诺。

**验收：** 最低支持版本能够加载 Studio、创建数据库并运行 v2 测试；不支持版本启动时给出清晰提示。

### R07【P2】Studio 代码可读性与类型约束落后于技术决策

**依据：** runner、documents、approvals 等模块存在整段逻辑压缩为单行的方法，公开接口缺少完整 JSDoc；与 `doc/studio-js-ts-decision.md` 中的过渡要求存在差距。

**建议：** 统一格式、拆分校验/生产/提交逻辑、补 JSDoc typedef 和公共接口注释；集中管理状态枚举与迁移规则。暂不要求全量迁移 TypeScript，但应把类型检查纳入后续评估。

**验收：** 核心领域对象有明确契约，跨模块字段与状态可以检查；格式调整与行为变更分开提交。

## 4. 待验证风险与后续专项审核

以下是应验证的目标，不代表已经确认整个 v2 缺失对应功能：

1. **恢复与幂等：** JSONL/manifest 是否足以重建状态；重复审批、重复提交、断点重跑是否产生重复效果；运行中崩溃任务如何恢复。仅有事件追加功能不等于具备完整事件回放。
2. **发布完整性：** release 封版后是否确实不可被生产路径修改；manifest 是否绑定所有文件、依赖、审批和 checksum；继承模式是否保持来源可追溯。
3. **调度可靠性：** 当前已新增任务调度与审核代码，不应继续笼统认为 v2 没有调度器；需专项测试阶段门、stale 传播、依赖环、并发容量和失败恢复。
4. **真实模型可靠性：** 补充超时、无效 JSON、内容截断、Token 预算、限流、重试上限和重复响应测试；可解析输出不能直接等同于生产完成。
5. **安全边界：** 单独验证 v2 的 workspace/release、符号链接、命令执行和审批权限。v1 的首命令白名单只是限制措施，并非完整沙箱；允许 node/npm 等解释器也不能阻止任意文件访问，不应直接继承其安全结论。
6. **产品入口：** 后续将根入口文档改为介绍 v2 和可运行流程，保留 v1 历史链接。无需为了代码目录整洁立即迁移整个 v1，也不安排 v1 功能开发。

## 7. 代码复审（2026-09-16，HEAD 8d3fa2f）

本节以当前 Studio v2 代码为准，覆盖初审后已经落地的改动。复审发现：R01 的同名文档覆盖问题已经通过 Artifact ID 文件名得到改善；R03 已有逐版本迁移；R04 已增加按 Artifact ID 重新读取权威状态。R02 也已加入 SQLite 事务和 outbox，但跨文件、数据库、事件的完整提交语义仍未闭合。

### C01【P0】阶段编排没有把 stageKey 传给调度器，可能跨阶段执行任务

**依据：** `src/studio/orchestration.js:3` 调用 `scheduler.runReady({versionId,agents,reviewer})`，没有传入当前 `stageKey`；`src/studio/scheduler.js:3` 遍历 `this.tasks.ready(versionId)`，没有按阶段过滤；`StudioTaskStore.ready()` 也只按版本和依赖筛选。

**复现：** 为同一版本建立一个 planning 任务和一个无依赖的 design 任务，只运行 planning 阶段；两个任务都会被执行并批准。

**风险：** 阶段门被绕过，下游正式产物可能在上游用户确认前生成，违背 v2 的“未满足上游阶段门不得正式启动”。

**建议：** `runReady` 必须接收并强制筛选 `stageKey`；同时检查阶段状态为 active，并在任务启动前确认版本、阶段门和依赖仍有效。增加“当前阶段运行不会触碰其他阶段任务”的回归测试。

### C02【P0】Bug 回归测试链接使用了错误的外键对象

**依据：** `src/studio/bugs.js:10` 把 `bugId` 写入 `artifact_dependencies.depends_on_artifact_id`，但该列外键引用 `artifacts(id)`，Bug ID 属于 `bugs(id)`。

**复现：** 创建 Bug 和测试 Artifact 后调用 `linkRegression()`，SQLite 返回 `FOREIGN KEY constraint failed`。

**风险：** 需求要求 Bug 绑定回归测试；当前公开 API 在正常数据下不可用。

**建议：** 增加专用的 Bug—测试关系表，或把关系建模为 `bug_impacts`/专门关联表；不要把 Bug ID 填入 Artifact 依赖图。补充成功、重复和跨版本拒绝测试。

### C03【P0】Release manifest 不完整，封版目录也没有真正只读保护

**依据：** `src/studio/versions.js:19` 只从数据库读取 Artifact 和 Approval，传给 `buildManifest()`；`src/studio/manifest.js:3-4` 的 manifest 没有 workspace 文件清单、文件 checksum、依赖闭包、测试证据和回滚信息。`versions.js` 中的 `filesOf()` 已实现但未被 seal 使用。`chmodSync(release,0o555)` 只作用于 release 根目录，未递归保护文件，且 Windows 下不能作为应用层只读保证。

**复现：** 封版后 manifest 只有 `artifacts/approvals/tests` 等元数据，`tests` 固定为空；fork 后数据库中没有继承的 Artifact 元数据。

**风险：** 无法证明发布包与批准 Artifact 的实际内容一致；发布文件可以被修改而不更新 manifest；release 不能满足“封版后只读”和可回滚审计要求。

**建议：** seal 前枚举受控目录并记录每个文件的相对路径、大小、checksum、Artifact 归属、依赖和测试证据；manifest 写入应原子化并在封版后校验。通过应用层拒绝对 release workspace 的写入，文件系统权限只作辅助。

### C04【P1】Artifact 继承可把 rejected/stale 产物直接伪装成 approved

**依据：** `src/studio/artifacts.js:5` 未检查 source 的状态、来源版本、checksum 或文件是否存在，直接以 `state:approved` 创建新 Artifact。

**复现：** 对 `state:rejected` 的 source 调用 `inherit()`，返回的新 Artifact 状态为 `approved`。

**风险：** 被拒绝、过期或不存在可验证内容的产物可以绕过审核成为下游正式输入；这直接破坏批准输入原则。

**建议：** `reuse` 只允许来源 Artifact 为 approved/user-approved 且 checksum 可验证；`fork/replace` 应创建 submitted/draft 状态并要求重新审核；记录 sourceVersion、sourceArtifact、inheritMode、checksum 和变更说明。

### C05【P1】forkVersion 只复制文件，不复制或登记继承 Artifact

**依据：** `src/studio/versions.js:20` 只 `copyTree(base.workspace_path,next.workspace_path)` 并写入 `version.forked` 事件，没有复制 Artifact、依赖、审批或 inherit 元数据。

**风险：** 新版本磁盘上看似有基线文件，但数据库查询不到对应产物；下游无法通过 Artifact 状态、审批和 checksum 正确消费这些文件，容易形成“文件存在、事实不存在”的双重状态。

**建议：** fork 必须通过 ArtifactStore 批量建立继承关系，明确 reuse/reference/fork/replace；对复制文件重新校验 checksum，并让新版本只使用登记后的 Artifact。

### C06【P1】event outbox 导出不是幂等的，崩溃可能产生重复审计事件

**依据：** `src/studio/events.js:7` 先 `appendFileSync()`，再更新 `exported_at`。两步之间进程崩溃时，重试会再次追加同一 `event_id`。

**风险：** JSONL 审计流出现重复事件；如果回放逻辑不是幂等的，可能重复应用状态或重复统计。

**建议：** 导出器按 event_id 去重，或使用带索引的事件文件/重建校验；写入和标记之间设计可恢复协议，增加“追加成功后崩溃”的故障注入测试。

### C07【P1】调度器的 Artifact、任务和审查状态不是一个原子提交

**依据：** `src/studio/scheduler.js:3` 先由 runner 创建 Artifact，再单独更新 `studio_tasks.artifact_id`，然后写 review、更新 Artifact 状态，最后迁移 Task。任一步失败都会留下孤儿 Artifact 或任务/Artifact 状态不一致。

**风险：** 恢复后任务可能是 failed，但 submitted Artifact 已存在；重复重试会产生多个未关联产物。

**建议：** 把同一 DB 内的任务、Artifact、Review 状态更新置于事务；为一次 attempt 设置幂等键；失败恢复时明确清理、复用或标记孤儿产物。文件系统提交仍需配合 outbox/补偿。

### C08【P1】依赖 API 没有校验版本归属和环路

**依据：** `src/studio/tasks.js:9` 只禁止任务自依赖，未检查两个任务存在、是否同一 version、是否形成环；`src/studio/impact.js:3` 对 Artifact 依赖也未校验两者存在、版本关系或环路。

**风险：** 可以建立跨版本依赖或 A→B→A 环路；ready 队列会永久等待，影响分析可能无限循环或产生跨版本污染。

**建议：** 插入依赖前校验实体、版本/继承关系及 DAG；在数据库或服务层增加唯一和归属约束；增加环路、跨版本、重复依赖和并发插入测试。

### C09【P1】底层 StageGateStore 可以绕过阶段任务和用户审批策略

**依据：** `src/studio/stages.js:8` 允许调用者直接执行 `reviewing → approved`；任务完成、Reviewer 结论和用户确认只在 `StudioStageOrchestrator.approveStage()` 中检查。StageGateStore 是公共导出模块，存在绕过编排器的入口。

**风险：** 任何直接使用底层 Store 的 CLI、脚本或 Agent 都可能把未完成阶段标为 approved，随后启动下游或封版。

**建议：** 将“状态存储迁移”和“业务阶段批准”分离；禁止公共低层 API 直接批准，或要求传入经过验证的 gate evidence/approval token；所有调用入口统一走事务化 orchestrator。

### C10【P2】ChangeSet 目前只有事件，没有可查询持久化模型

**依据：** `src/studio/changes.js:4` 只生成 UUID、追加事件并返回内存对象，没有对应表、读取 API、Artifact 关联或版本约束。

**风险：** 进程重启后无法按版本查询 change-set，无法作为 Stage 0 的正式交付物参与 manifest、审批和影响分析。

**建议：** 增加 changesets 表和变更项表，或将其作为正式 Artifact 存储；至少绑定 version、baseVersion、变更项、状态、checksum 和审批。

### C11【P2】独立 Layer 输入和输出边界仍可越过工作区，且读取无资源上限

**依据：** `src/studio/layers.js:6-10` 使用 `resolve(input)`、递归 `statSync/readdirSync` 和 `readFileSync`，没有项目根边界、符号链接拒绝、单文件大小/总字节限制；`output` 和 `logPath` 也可解析到任意绝对路径。

**风险：** 被错误配置或被 Agent 控制的 layer 可以读取工作区外文件、跟随 symlink、把大量文件内容送入模型，或把产物/日志写到任意位置。

**建议：** 为 layer 绑定 workspace root；对输入、输出和日志统一 safeJoin/assertNoSymlink；限制文件数量、单文件大小、总读取字节和 prompt 长度；禁止默认跟随 symlink。

### C12【P1】审批者和 Reviewer 身份可由调用方自报，版本批准未核验审批事实

**依据：** `src/studio/approvals.js:5` 只校验 `approverType` 是否属于固定字符串集合；`src/studio/reviews.js:4` 只校验 reviewer 是非空字符串，没有 Agent/用户身份或权限绑定。`src/studio/versions.js:18` 只检查阶段状态及 stale/rejected Artifact，不查询必要的 Artifact Review、经理审批和用户确认记录。

**风险：** 任意可调用方可以把自己标记为 manager、user 或 reviewer，或直接拼出满足状态条件的批准结果；审计记录有名字但没有可信主体。

**建议：** 引入不可伪造的 actor/role/context，由授权层或受控服务注入而不是由请求体决定；版本和阶段批准必须验证所需审批集合、审批对象、审批顺序与用户确认事件。

### C13【P1】版本状态迁移没有封闭，released 版本可以再次 approve 并复用 release 路径

**依据：** `src/studio/versions.js:18` 未限制当前版本状态，直接 `UPDATE versions SET status='approved'`；`seal()` 只检查 approved，并按“当天 + 版本号”生成 release 路径。

**风险：** 已 released 版本可被改回 approved，再次封版时可能覆盖同一路径或重新生成不一致的发布物。

**建议：** 明确定义 version 状态机，使用带旧状态条件的原子更新；released/sealed 为终态，禁止回退和重复 seal，release 目录已存在时必须拒绝而不是覆盖。

### C14【P1】版本创建和封版流程跨目录、数据库、事件，不具备恢复协议

**依据：** `src/studio/versions.js:16` 先创建 workspace/子目录，再分别插入 version 和 stages；`:19` 依次 copy workspace、写 manifest、chmod、更新数据库、追加事件，未使用事务、锁或补偿记录。

**风险：** 进程在任意步骤中断，会留下半初始化版本、半成品 release、数据库状态与磁盘状态不一致，重试还可能复用残留路径。

**建议：** 数据库操作使用事务和幂等键；封版使用临时 release 目录、完整校验、原子 rename 和 seal marker；启动时扫描并恢复/清理未完成操作。

### C15【P1】运行中任务没有租约和原子 claim，恢复可能与旧 Worker 重复执行

**依据：** `src/studio/tasks.js:14` 通过先读取任务再更新状态，没有 `WHERE status=...` 的条件 claim；`:12` 的 `recoverRunning({maxAgeMs=0})` 默认把所有 running 任务直接改为 failed。

**风险：** 旧 Worker 仍在调用模型时，恢复器可能先将任务标记 failed，新 Worker 随后重跑，造成重复模型调用、重复文件和多个 Artifact。

**建议：** 增加 worker_id、lease_until、heartbeat 和 attempt token；用条件 UPDATE 原子认领任务；恢复只处理过期租约，并让提交结果校验 attempt token。

### C16【P1】文档 Runner 传给模型的输入只有 Artifact 元数据，缺少正文/文件内容

**依据：** `src/studio/runner.js:5` 生成的 `inputText` 只有 `name` 和 `state`；`StudioDocumentStore` 返回的输入对象和数据库 `artifacts` 行也没有正文、文件路径或可读取内容。

**风险：** 下游 Agent 形式上收到了 approved 输入，实际上无法阅读上游策划、规格或测试文档，容易产出脱离基线的内容。

**建议：** Artifact 元数据应关联受控文件清单；Runner 在 workspace 边界内读取并校验 checksum 后，把受限正文/结构化数据/文件引用放入模型上下文，并设置大小与敏感信息策略。
